# 16 — NetGuard V2.1 Analytics Foundations Specification

## 1. System Mission & Scope

NetGuard V2.1 introduces formal, authoritative analytics and metrics capabilities to the Security Operations Center (SOC). 
Building upon V0 (telemetry ingestion & RBAC) and V1 (alerts, incidents, and investigation workflows), V2.1 establishes:
- Standardized, authoritative metric definitions.
- Rigorous Mean Time to Detect (MTTD) timestamp semantics and formulas.
- Bounded time-series historical trends for alerts and incidents (`24h`, `7d`, `30d`).
- Comprehensive REST APIs for dashboard summaries, trends, and operational health.
- Clear authorization boundaries and query performance guardrails.

## 2. Authoritative Metric Definitions

### 2.1 Incident Metrics
- **Active Incidents**:
  $$\text{Count of incidents where } \text{status} \in (\text{'OPEN'}, \text{'INVESTIGATING'}, \text{'CONTAINED'}, \text{'RESOLVED'})$$
  *(Excludes `CLOSED` incidents, which are archived).*
- **Unassigned Incidents Queue**:
  $$\text{Count of active incidents where } \text{assigned\_to IS NULL}$$
- **Incident Severity Distribution**:
  Grouped count of incidents by severity rating: `SEV1` (Critical), `SEV2` (High), `SEV3` (Medium), `SEV4` (Low).
- **Incident Status Distribution**:
  Grouped count of incidents by workflow status: `OPEN`, `INVESTIGATING`, `CONTAINED`, `RESOLVED`, `CLOSED`.

### 2.2 Alert Metrics
- **Open Actionable Alerts**:
  $$\text{Count of alerts where } \text{status} \in (\text{'NEW'}, \text{'IN\_PROGRESS'})$$
- **Alert Severity Breakdown**:
  Grouped counts by severity: `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`.
- **Alert Triage Status Breakdown**:
  Grouped counts by triage state: `NEW`, `IN_PROGRESS`, `RESOLVED`, `DISMISSED`.

### 2.3 Mean Time to Detect (MTTD)
- **Concept**:
  MTTD measures the operational efficiency of the detection and promotion pipeline—specifically the duration from when a network packet was captured by Snort to when an actionable alert was created in NetGuard.
- **Authoritative Timestamp Semantics**:
  - `security_events.timestamp`: The physical detection timestamp recorded in the Snort sensor packet header.
  - `alerts.created_at`: The persistent timestamp recorded when NetGuard created the alert record (either via auto-promotion or manual promotion).
- **Mathematical Formula**:
  $$\text{Detection Latency}_i = \text{alert}_i\text{.created\_at} - \text{security\_event}_i\text{.timestamp}$$
  $$\text{MTTD} = \frac{1}{N} \sum_{i=1}^N \text{Detection Latency}_i$$
- **Inclusion & Exclusion Rules**:
  1. Only alerts with a valid `security_event_id` reference are included.
  2. Alerts must satisfy $\text{Detection Latency}_i \ge 0$ (clock skew protection).
  3. Manually created alerts without an underlying telemetry event are **excluded** to prevent metric distortion.
  4. If $N = 0$, the metric status is `"insufficient_data"` and `averageSeconds` is `null`.

## 3. Time Windows & Bucketing Strategy

All analytics trend endpoints enforce bounded time windows to prevent expensive full-table scans:

| Time Window | Parameter | Bucket Interval | Total Buckets | Primary Use Case |
| :--- | :--- | :--- | :--- | :--- |
| **Past 24 Hours** | `timeRange=24h` | 1 Hour (`1h`) | 24 data points | Immediate operational shift monitoring |
| **Past 7 Days** | `timeRange=7d` | 1 Day (`1d`) | 7 data points | Weekly operational review & trend analysis |
| **Past 30 Days** | `timeRange=30d` | 1 Day (`1d`) | 30 data points | Monthly SLA & posture assessment |

### Zero-Filling Requirement
If a specific hour or day in the requested window contains zero alerts or incidents, the API **must** return that bucket with count `0` rather than omitting the timestamp. This guarantees uniform chart axes on the frontend.

## 4. REST API Contracts (`/api/analytics`)

### 4.1 Global Conventions
- All analytics endpoints are mounted at `/api/analytics`.
- Authentication: `Authorization: Bearer <jwt-token>` required.
- Authorization: Read-only access permitted for `ADMIN`, `ANALYST`, and `VIEWER`.
- Standard JSON envelope: `{ "success": true, "data": { ... } }`.

---

### 4.3 `GET /api/analytics/trends`
Retrieves uniform time-series bucket data for alerts and incidents.

- **Query Parameters**:
  - `timeRange` (optional, default `'24h'`): `'24h' | '7d' | '30d'`.
  - `entity` (optional, default `'all'`): `'alerts' | 'incidents' | 'all'`.
- **Response `200 OK`**:
  ```json
  {
    "success": true,
    "data": {
      "timeRange": "24h",
      "bucketInterval": "1h",
      "buckets": [
        {
          "timestamp": "2026-10-16T09:00:00.000Z",
          "alertsTotal": 2,
          "alertsCritical": 1,
          "alertsHigh": 1,
          "alertsMedium": 0,
          "alertsLow": 0,
          "incidentsDeclared": 1,
          "incidentsResolved": 0
        }
      ]
    }
  }
  ```

### 4.4 `GET /api/analytics/mttd`
Retrieves detailed Mean Time to Detect statistics and latency distribution.

- **Query Parameters**:
  - `timeRange` (optional, default `'24h'`): `'24h' | '7d' | '30d'`.
- **Response `200 OK`**:
  ```json
  {
    "success": true,
    "data": {
      "timeRange": "24h",
      "averageSeconds": 14.8,
      "medianSeconds": 12.0,
      "minSeconds": 3.5,
      "maxSeconds": 48.2,

        {
          "timestamp": "2026-10-16T12:00:00.000Z",
          "averageSeconds": 13.2,
          "count": 2
        }
      ]
    }
  }
  ```
