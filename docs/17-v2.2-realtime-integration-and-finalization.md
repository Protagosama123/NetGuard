# 17 — NetGuard V2.2 Realtime Integration & Finalization Specification

## 1. System Mission & Boundary

NetGuard V2.2 completes the planned scope of the NetGuard mini-SOC. It introduces authenticated, low-latency realtime push delivery via WebSockets while maintaining strict consistency with the authoritative PostgreSQL datastore and REST recovery APIs.

### Golden Rules of Realtime in NetGuard
1. **PostgreSQL is Authoritative**: Realtime messages are notifications of state changes, never the primary source of truth.
2. **REST is the Baseline & Recovery Vehicle**: Initial page loads and post-reconnection resynchronizations always pull authoritative state via REST.
3. **Post-Commit Publication Only**: A realtime event is dispatched *strictly after* the database transaction commits successfully. If a database operation fails or rolls back, no event is emitted.
4. **Resilience to Network Drops & Duplicate Delivery**: Clients must handle duplicate, delayed, or out-of-order notifications safely through entity ID and timestamp checks.

## 2. WebSocket Gateway Architecture

### 2.1 Connection Handshake & Authentication
- **Endpoint**: `ws://<host>:<port>/ws` (or `wss://` in production / TLS).
- **Authentication**: JWT token supplied during connection handshake via URL query parameter:
  `ws://localhost:3000/ws?token=<jwt-bearer-token>`
- **Handshake Validation**:
  - The server extracts `token` from the upgrade request URL.
  - Verifies token validity and signature using `AuthService.verifyToken(token)`.
  - If token is missing, invalid, expired, or belongs to a deactivated user: the upgrade request is rejected with `HTTP 401 Unauthorized` and the connection is closed immediately.
  - Upon successful verification, the client socket is bound with authenticated user session metadata (`userId`, `role`, `email`).

### 2.2 Connection Lifecycle & Heartbeat
- **Heartbeat Interval**: 25 seconds.
- **Protocol**: Server issues `ping` frame; client automatically replies with `pong`.
- **Termination Policy**: If a client socket misses two consecutive heartbeat intervals (30s timeout), the server marks the socket dead and terminates the connection.

## 3. Standardized Event Contracts

All realtime messages conform to a standard JSON envelope:

```json
{
  "event": "alert:created",
  "timestamp": "2026-10-17T08:35:00.000Z",
  "data": { ... }
}
```

### 3.1 Event Catalog

| Event Name | Trigger Condition | Payload Schema | Target Roles |
| :--- | :--- | :--- | :--- |
| `alert:created` | Alert created (auto-promoted or manual) | `{ alert: Alert }` | All Authenticated |
| `alert:status_changed` | Alert triage status updated | `{ id: number, status: AlertStatus, updatedAt: string }` | All Authenticated |
| `incident:created` | Formal incident declared | `{ incident: Incident }` | All Authenticated |
| `incident:status_changed`| Incident status updated | `{ id: number, status: IncidentStatus, resolvedAt?: string, updatedAt: string }` | All Authenticated |
| `incident:assigned` | Incident assigned or cleared | `{ id: number, assignedTo: number \| null, assignee?: { id: number, email: string } }` | All Authenticated |
| `investigation:entry_added`| New finding/action recorded | `{ incidentId: number, entry: InvestigationEntry }` | All Authenticated |
| `telemetry:event_ingested`| Raw Snort detection event saved | `{ event: { id: number, signatureId: number, priority: number, sourceIp: string, destinationIp: string, createdAt: string } }` | All Authenticated |

## 4. Client-Side Resynchronization & Deduplication Protocol

### 4.1 State Machine
The client WebSocket manager maintains an explicit connection state:
- `CONNECTING`: Establishing socket connection.
- `CONNECTED`: Active authenticated socket with passing heartbeats.
- `RECONNECTING`: Re-establishing dropped socket with exponential backoff.
- `DISCONNECTED`: Terminated or logged out.

### 4.2 Exponential Backoff Reconnection
When a socket connection drops unexpectedly:
1. Reconnection retry intervals follow exponential backoff: $1\text{s} \rightarrow 2\text{s} \rightarrow 4\text{s} \rightarrow 8\text{s} \rightarrow \text{max } 10\text{s}$.
2. Maximum 10 retry attempts before pausing with manual "Reconnect" button in UI.

### 4.3 Mandatory REST Resynchronization on Reconnect
Because events could have occurred while the client was disconnected or reconnecting:
1. As soon as the socket transitions from `RECONNECTING` to `CONNECTED`, the client initiates a full REST refresh:
   - `GET /api/analytics/summary`
   - `GET /api/analytics/trends`
   - `GET /api/incidents`
   - `GET /api/alerts`
2. This guarantees zero state drift regardless of network instability.

### 4.4 In-Memory Deduplication
- When receiving entity update events (`alert:status_changed`, `incident:status_changed`), the client compares `updatedAt` timestamps. Older or duplicate events are ignored.

## 5. Security & Authorization Safeguards
- **Sensitive Fields Redacted**: Operator password hashes and system credentials are never broadcast over WebSockets.
- **Role Enforcement**: `VIEWER` users receive realtime notification of updates, but UI controls remain read-only.
- **Connection Rate Limiting**: Up to 10 concurrent connections per operator account.
