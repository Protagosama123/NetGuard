# 08 — Alerts & Incident Management Specification

## 1. Architectural Distinction: Events vs. Alerts vs. Incidents

NetGuard strictly separates three tiers of security data:

```
[Raw Network Telemetry]       [Actionable Item]             [Coordinated Response]
   security_events       -->       alerts             -->         incidents
   (Immutable Sensor Log)       (Triage & Validation)          (Investigation & Resolution)
```

1. **Security Event**: Immutable record generated by a Snort sensor. Captures exact packet details, signature matches, IP endpoints, and packet payload.
2. **Alert**: A normalized item requiring operator triage. An alert is created when an event matches alert criteria (e.g., Priority 1 or 2) or is manually promoted by an analyst. Multiple alerts may share similar attack patterns or IP origins.
3. **Incident**: An active operational case that tracks containment, root cause investigation, impact, and formal resolution. One incident links one or more alerts.

---

## 2. Alert Lifecycle & State Transitions

### Statuses
- **`NEW`**: Default state upon ingestion/creation. Awaiting initial triage.
- **`IN_PROGRESS`**: Operator is evaluating, investigating, or correlating the alert.
- **`RESOLVED`**: Threat confirmed, addressed, or linked to a resolved incident.
- **`DISMISSED`**: False positive, authorized penetration test, or non-actionable noise.

### Valid Transitions
```
        +-----------------------------------+
        |                                   |
        v                                   |
     [NEW] --------> [IN_PROGRESS] --------> [RESOLVED]
       |                    |
       +---> [DISMISSED] <--+
```
- From `NEW`: Can transition to `IN_PROGRESS` or `DISMISSED`.
- From `IN_PROGRESS`: Can transition to `RESOLVED`, `DISMISSED`, or return to `NEW`.
- From `RESOLVED` / `DISMISSED`: Can be reopened to `IN_PROGRESS` if new evidence emerges.

### Promotion Rules (Event $\rightarrow$ Alert)
- **Automatic Promotion**: Any ingested `security_event` with `priority === 1` (High) or `priority === 2` (Medium) automatically produces an associated `alert` with status `NEW`.
- **Manual Promotion**: An operator can manually promote any low-priority or informational security event to an alert via `POST /api/alerts/promote`.

---

## 3. Incident Lifecycle & State Transitions

### Statuses
- **`OPEN`**: Incident created. Initial scope and severity set.
- **`INVESTIGATING`**: Active forensic inquiry or root cause analysis underway.
- **`CONTAINED`**: Attacker access severed, affected systems isolated, or threats mitigated.
- **`RESOLVED`**: Remediation complete, vulnerability patched, or incident concluded. Requires `resolution_summary`.
- **`CLOSED`**: Post-incident review completed. Record locked against routine edits.

### Valid Transitions
```
[OPEN] ---> [INVESTIGATING] ---> [CONTAINED] ---> [RESOLVED] ---> [CLOSED]
  ^               |                   |                ^
  |               +-------------------+----------------+
  +----------------------------------------------------+ (Reopened)
```

### Constraints & Business Rules
1. **Resolution Summary**: When updating status to `RESOLVED` or `CLOSED`, a non-empty `resolution_summary` is mandatory. The `resolved_at` timestamp is set automatically.
2. **Reopening**: Moving from `RESOLVED` or `CLOSED` back to `INVESTIGATING` clears the `resolved_at` timestamp.
3. **Transaction Safety**: Linking an alert to an incident updates the join table `incident_alerts` and automatically transitions the alert's status to `IN_PROGRESS` if it was `NEW`.

---

## 4. Assignment Model

- **Assignee Eligibility**: Incidents may only be assigned to active system users holding the `ADMIN` or `ANALYST` role.
- **Separation from Status**: An incident can be `OPEN` and assigned, or `INVESTIGATING` with reassignment. Status represents workflow progress; assignment represents responsibility.
- **Unassignment**: An authorized operator may clear the assignment (`assigned_to = null`).

---

## 5. Investigation Timeline

- Each incident maintains an append-only timeline of `investigation_entries`.
- **Entry Types**:
  - `NOTE`: General analytical notes or observations.
  - `ACTION_TAKEN`: Steps executed (e.g. firewall rule applied, host isolated).
  - `CONTAINMENT`: Formal containment action record.
  - `EVIDENCE`: Log snippets, indicators of compromise (IOCs), or packet artifacts.
- Entries are strictly attributed to the authenticated operator (`author_id`) and ordered chronologically (`created_at ASC` or `DESC` as requested).
